## 3. 各问题的处理与操作说明

### 3.1 顶部公司数量

原实现会在应用外壳加载公司目录，并根据数量显示“当前公司”或“可管理 N 家公司”。
现已移除该查询、状态和文字渲染，仅保留无文字弹性占位，从而保持右侧操作按钮位置不变。

### 3.2 员工所在部门

员工接口已经返回当前有效任职所指向组织的 `organizationName`，员工表也一直渲染该值。
本次把业务列名改为“所在部门”。当前库中的组织分类为 4 个 `COMPANY` 和 152 个
`DEPARTMENT`，没有可可靠区分“一级部门”和“末级小组”的额外类型，因此不根据名称或层级
伪造另一个部门字段；这里展示员工当前直接归属的部门/小组。

如果后续要同时展示“一级部门”和“所在小组”，需要先在组织导入合同中明确部门层级类型，
再由后端返回两个独立字段。

### 3.3 规则试算排版

原说明文字使用全局 `.form-help`，该样式带负上边距；它紧跟动态“添加打卡”区域时会与按钮
挤在一起。现在：

- 动态打卡列表使用独立网格和下间距；
- 说明与“运行试算”归入独立操作区；
- 说明使用局部样式，边距归零。

### 3.4 考勤规则新增原因与正确操作

原因有四点：

1. 规则按公司隔离，而账号可管理 4 家公司；系统为避免写错公司，不自动选择第一家公司。
2. 页面顶部的“新建策略绑定”不是新增规则按钮；没有已选规则版本时它会禁用。
3. 真正的“创建策略草稿”入口原先位于版本历史和详情之后，容易被误认为不存在。
4. 只有读权限时管理控件原先直接隐藏，没有说明缺少哪项权限。

本次已在未选公司时增加显式提示，把“创建策略草稿”前移到版本生命周期区域顶部，将页头动作
改名为“绑定规则到考勤组”，并为只读账号显示所需权限说明。

操作顺序：

1. 使用具备 `ATTENDANCE_SETUP:MANAGE_POLICY` 权限的账号进入“考勤规则”。
2. 先选择公司，再选择“用餐时段扣除”“迟到宽限”或“每月迟到豁免”。
3. 在“创建策略草稿”中填写生效日和至少 2 个字符的变更原因，创建草稿版本。
4. 打开新草稿，调整参数和有效期，填写变更原因后保存。
5. 先执行“校验”，校验通过后执行“发布”。
6. 发布后点击“绑定规则到考勤组”，把已发布版本绑定到对应考勤组。

已发布版本不可直接覆盖；制度变化应基于现有版本再创建未来生效的草稿。

### 3.5 得力打卡 API 与不显示的原因

可以由后端调用得力 E+ API，但不应让浏览器直接携带 App Key/Secret 请求供应商。当前后端已有：

- 得力签名和分页客户端，服务端调用 `/v2.0/cloudappapi` 的 `CHECKIN/checkin_query`；
- `POST /api/v1/attendance-sources` 注册来源；
- `POST /api/v1/attendance-source-jobs` 发起同步；
- 来源、任务、OA 单据的只读查询接口。

当前看不到数据的直接原因是：得力功能默认关闭、运行进程未注入得力配置、数据库中来源和任务为
0、615 名员工都没有得力 `ext_id/user_id`，也没有按具体来源确认的绑定。因此页面只能得到空列表，
即使贸然同步，人员也无法形成可信匹配。

正式启用至少需要：

1. 在后端运行环境安全注入 `DELI_EPLUS_ENABLED=true`、Base URL、App Key、App Secret、时区和凭据引用，重启后端；凭据不得放入前端或数据库业务字段。
2. 使用有 `ATTENDANCE_SOURCE:CONFIGURE` 和目标公司数据范围的账号注册得力来源。
3. 确认得力租户已初始化，并按具体来源完成员工 `ext_id/user_id` 的人工核验和确认绑定。
4. 确保目标员工的考勤组、地点、日历、班次和规则均已发布，目标期间允许写入。
5. 使用 `ATTENDANCE_SOURCE:RUN` 发起同步，并在“同步记录”检查成功、隔离和失败数量。
6. 同步后仍需运行考勤计算并发布正式投影，才能进入报表和工作台。

当前代码仍缺少 V27/V28 所要求的得力初始化确认、定时调度、连接探测以及按来源确认人员绑定的
完整管理服务/UI；迁移表存在不代表这些运行能力已经接通。因此目前只能认定为“API 客户端和手工
同步入口存在”，不能认定为“配置密钥后即可生产自动出数”。

本次同时把在线来源、OA 来源和同步任务的空态文案改为可操作的原因提示，避免继续显示泛化的
“暂无数据”。

### 3.6 OA 单据查询

仅连接 OA 数据库不会直接展示单据。当前正式代码只实现：

- 默认关闭、只读的小连接池；
- 固定参数 SQL `SELECT id, code FROM org_member WHERE id = ?`；
- 六类表单的截图字段白名单和纯转换骨架。

目前 OA 实库表结构、审批状态、主从外键、业务枚举、稳定水位、撤销语义、时区和数据范围均为
`NOT_VERIFIED`；六类业务表的正式固定 SQL、同步任务和来源注册也未实现。必须先按
`docs/contracts/oa-attendance-form-mapping-signoff-matrix.md` 完成只读联调签字，再实现适配器、
注册来源、同步入本系统的 `oa_attendance_document`，页面才会展示。

### 3.7 报表

报表页面不会直接查询任意原始表，也不会因为数据库连通就自行计算。正式模式只读取所选公司、
所选月份已发布且当前账号有权限查看的不可变月度投影。当前库的正式投影数量为 0，所以公司目录
和报表内容都为空。

仓库已有受信任的进程内发布入口
`AttendanceReportProjectionPublicationUseCase.publish(PublishCommand)`，但全月计算结果持久化、
月结编排、OA 事实和时间账户快照尚未接通，不能通过前端提交事实来绕过。

正确链路是：来源同步 → 人员/配置匹配 → 日考勤计算 → 月度结算/复核 → 正式投影发布 → 报表查询。
本次已把报表空态改为明确提示“需完成考勤计算与正式投影发布”。

### 3.8 首页考勤工作台

首页不是直接统计原始打卡表。管理工作台需要当前公司、当天数据已包含在最新
`PUBLISHED` 投影中；个人工作台还需要登录主体唯一绑定员工以及 `SELF` 数据范围。当前投影为 0，
所以显示“尚未生成”符合正式数据边界。

正确链路与报表相同，并且投影的 `dataAsOf` 必须覆盖当天。仅连接数据库、只有员工或原始打卡，
都不足以显示。此次已把工作台空态补充为“同步后还需计算并发布正式投影”。
