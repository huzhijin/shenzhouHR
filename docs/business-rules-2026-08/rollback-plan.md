# 2026-08 业务规则对齐分阶段回滚方案

## 原则

回滚按部署的反方向执行：**先停得力调度，再回退应用制品，最后才考虑删除 V48 结构**。优先 roll forward 或保留向前兼容的新增结构，避免为了代码问题丢失补卡、同步日志和 OA 映射数据。

本文是回滚方案，不表示已演练或已在任何环境执行。演练证据必须在部署窗口前另行保存。

## 启动条件和授权

出现以下任一情况时，发布负责人暂停后续阶段并召集 HR、运维、开发和 DBA：

- V48 部分执行、约束失败或 Flyway 历史异常；
- 应用无法启动、持续 5xx、权限边界失效或数据跨公司；
- 新公式、迟到转旷班、补卡、加班分类或调岗分配产生系统性错误；
- 得力同步重复写入、跳过水位、泄漏凭据或造成不可控负载；
- HR 判定新规则必须暂停。

只有变更单指定的回滚负责人可以下令。执行人必须记录触发时间、影响公司/月份、最后成功阶段、当前写入状态和选择的恢复点。

## 阶段 1：停止得力调度

适用于同步异常或任何需要稳定写入面的故障，也是其他回滚阶段的第一步。

1. 将 `SHENZHOUHR_DELI_AUTO_SYNC_ENABLED=false`，重启应用使条件化调度 bean 退出。
2. 不删除失败日志，不手工推进最后成功同步时间。
3. 记录停用前最后一个 `SUCCESS` 的时间和失败区间。
4. 保留得力来源凭据配置；只有凭据泄漏时才按安全流程轮换。
5. 修复后从最后成功水位重试，确认失败区间记录全部补齐。

仅修改 cron 不能可靠停止已经装配的任务；紧急停止使用启用开关。不得通过红黄灯或月结门禁代替实际停用，因为本规则明确没有这些功能。

## 阶段 2：回退应用制品

V48 主要增加可空或有默认值的字段以及新表，旧应用通常可以忽略，因此代码故障时优先保留 V48：

1. 停止当前应用，禁止补卡审批、重算、报表发布和同步写入。
2. 校验部署前保存的旧 JAR/前端制品 SHA-256。
3. 恢复旧制品和部署前环境配置，保持应用内 Flyway 关闭。
4. 启动并验证健康检查、登录、核心只读报表和公司权限边界。
5. 将回滚期间产生的新规则数据标记为受影响区间，交由 HR/数据负责人决定后续重算或重新发布。

当前实现没有 `businessRules2026_08` 总开关，不能把“关闭 feature flag”当作可执行步骤。旧公式回退必须通过经过验证的旧制品完成。

## 阶段 3：业务结果处置

应用回退不会自动撤销已经计算或发布的业务结果：

- 不覆盖、删除或原地修改已发布的不可变报表投影。
- 记录受影响的公司、员工、业务日、投影 ID、规则版本和数据截止时间。
- 未发布结果可停止发布并按支持的重算流程处理。
- 已发布结果由 HR 和数据负责人决定是否发布更正版本；更正必须带原因、版本和审计记录。
- 补卡批准记录和合成证据保留，不得为了恢复配额删除。
- 切换前后公式不同，比较报告必须标注口径，不能把差异当作数据丢失。

## 阶段 4：数据库回退（最后手段）

只有旧应用无法容忍 V48 结构、V48 本身错误且无法前向修复，或安全/合规要求必须删除数据时，才考虑执行 [ROLLBACK_V48__business_rules_alignment_schema.sql](../../backend/src/main/resources/db/migration/ROLLBACK_V48__business_rules_alignment_schema.sql)。

### 执行前门禁

- [ ] 应用、调度、审批、重算和报表发布全部停止。
- [ ] 已创建并验证数据库全量备份。
- [ ] 已单独导出补卡申请、得力同步日志和 OA 枚举映射，并记录行数与校验值。
- [ ] 已确认没有代码、查询或报表继续引用待删除字段。
- [ ] DBA 已审阅 MySQL 版本下的 `DROP CHECK`、`DROP INDEX` 和隐式提交行为。
- [ ] HR/数据负责人书面接受下表的数据影响。
- [ ] 已制定 Flyway 历史恢复方案；不会使用无依据的 `repair`。

### 数据影响

| 回退动作 | 不可恢复影响（除非从备份恢复） |
|---|---|
| 删除三类加班字段 | 丢失已投影的计薪、转调休、义务及汇总分钟 |
| 删除 OA 上下文加班类型 | 丢失已分类证据上下文 |
| 删除 `deli_sync_log` | 丢失同步时间、数量、水位区间和错误历史 |
| 删除 `oa_enum_mapping` | 丢失已验证的 OA 枚举配置 |
| 删除 `punch_correction_request` | 丢失申请、审批、配额和审计链 |
| 删除 `leave_type` | 丢失日事实中的具体假别 |
| 删除补卡 capability | 撤销相关角色能力映射 |

### 执行与核验

使用受控迁移账号从标准输入执行回退文件，凭据不得出现在命令行或日志。脚本执行后运行文件末尾的 `information_schema` 只读查询，预期相关对象为 0；随后验证旧应用启动和核心只读路径。

手工执行回退脚本不会自动撤销 `flyway_schema_history` 中的 V48 成功记录。数据库结构与 Flyway 历史一旦不一致，必须保持应用停止，并由 DBA 选择“从迁移前备份恢复”或“创建新的前向修复迁移”；不得直接 `flyway repair` 掩盖差异。

## 阶段 5：恢复服务

- [ ] 健康检查、登录、公司边界和审计写入通过。
- [ ] 报表明确使用恢复后的规则版本，受影响投影已隔离或更正。
- [ ] 得力同步仍保持关闭，直到水位和重复数据检查通过。
- [ ] HR 已收到回滚范围、员工影响和后续处理说明。
- [ ] 事件记录包含时间线、根因、数据影响、恢复点和防复发动作。

重新启用得力时，先在单个受控环境验证从最后成功水位补齐，再恢复 `0 0 * * * ?` 整点计划。恢复生产和观察属于新的外部动作，不能因本文档存在而自动视为完成。
