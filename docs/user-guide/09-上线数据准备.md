# 09 上线数据准备

## 先看结论

客户服务器完成安装后，不能只导入员工或接通数据源就直接使用。正式出勤结果至少依赖：公司、组织、员工及任职、账号权限、地点、班次、工作日历、考勤组及人员归属、已发布规则、打卡/OA 证据、计算结果和正式月度投影。

本章把资料分为“必须准备”“按启用功能准备”和“当前仍待开发”三类。任何标为待开发的项目都不能通过手工 SQL 绕过，因为这会破坏幂等、版本、台账和审计。

## 一、所有客户都必须准备的数据

| 顺序 | 数据 | 客户需要提供 | 当前录入方式 | 验收重点 |
| ---: | --- | --- | --- | --- |
| 1 | 公司 | 公司全称、简称、唯一编码、启停状态 | 首次安装初始化或受控脚本 | 每家公司是独立数据边界 |
| 2 | 组织 | 部门编码、名称、上级部门、公司、启停及生效日 | 人员导入或组织维护页面 | 无断层、无循环、公司不串用 |
| 3 | 员工 | 工号、姓名、状态及必要的人事属性 | 人员导入或员工页面 | 工号稳定且唯一 |
| 4 | 任职 | 员工、公司、所在部门、入离职/调岗生效时间 | 人员导入或任职页面 | 每名在职员工恰有一个当前有效任职 |
| 5 | 管理账号 | 登录名、责任人、角色、公司/部门数据范围 | 账号管理 | 至少一名可登录管理员，范围最小化 |
| 6 | 地点 | 地点编码、名称、时区、可使用公司 | 考勤组页面的地点区域 | 物理地点不是部门，时区准确 |
| 7 | 班次 | 上下班、休息、跨日、版本生效日 | 班次页面 | 工作段不重叠且覆盖核算日期 |
| 8 | 工作日历 | 每天是工作日、周末、法定节假日或调休工作日 | 工作日历页面 | 每个核算日均有权威日型 |
| 9 | 考勤组 | 公司、地点、班次、日历、生效期间 | 考勤组页面 | 引用均属于同一公司且已发布 |
| 10 | 人员归属 | 员工、考勤组、生效日 | 考勤组分配人员 | 每名应考勤员工每天恰有一个有效组 |
| 11 | 考勤规则 | 参数、适用范围、生效日、发布状态 | 考勤规则页面 | 草稿不参与正式计算 |

当前正式页面和运行时只接入“用餐扣除、迟到宽限、每月迟到豁免”三类规则。早退、缺卡与补签、打卡配对、加班认定、出勤率虽然有数据库起步记录，但还不是完整的可维护生产功能。客户必须先确认这些口径，再补齐页面、接口、解析和回归测试，不能只改数据库参数。

## 二、人员导入文件的推荐顺序

1. 先导入组织；
2. 再导入员工；
3. 再导入任职；
4. 需要计算年假资格时，再导入入职前累计工龄；
5. 对每个批次执行预检、差异确认和发布；
6. 发布后按公司核对组织数、员工数、当前任职数和失败行；
7. 最后分配考勤组并按需开通登录账号。

累计工龄导入记录的是员工入职前的服务年限，字段包括工号、累计天数、业务日期和原因。它只参与年假资格/档位判断，不是年假期初余额，二者不能混用。

## 三、期初年假、调休和认可加班余额

### 业务上是否需要

若系统从年中切换、员工仍有历史结余，以下期初数是正式上线必需数据：

- 年假剩余；
- 调休剩余；
- 已认可但尚未结转/使用的加班余额；
- 每笔余额的基准日、到期日和来源说明；
- 必要时，余额对应的政策版本和任职周期。

如果客户明确从某一日期零余额起算，也必须由 HR 书面确认“全部账户期初为 0”，不能用缺数据代替零余额。

### 当前系统状态

数据库和领域模型预留了时间账户及 `OPENING` 台账类型，但当前没有可用的期初余额页面、REST 接口或 Excel 导入发布链。因此现在不能安全录入年假/调休期初数，本人的“我的假期”和年假报表也不能据此承诺生产可用。

上线前需要新增受控的 `TIME_ACCOUNT_OPENING` 批量导入，至少包含：

| 字段 | 说明 |
| --- | --- |
| 批次号 | 客户侧稳定且不可重复的批次标识 |
| 工号 | 与当前员工唯一匹配 |
| 账户类型 | 年假、调休、认可加班或签字确认的其他类型 |
| 期初小时 | 非负数，建议保留两位小数 |
| 余额基准日 | 该余额截至哪一天 |
| 到期日 | 无到期规则时可空 |
| 公司/任职周期 | 防止跨公司或二次入职串账 |
| 政策版本 | 年假等规则型账户必须可追溯 |
| 来源说明 | 客户原账、审批批次或调整原因 |

实现必须具备模板下载、预检、整批失败、差异确认、幂等发布和审计。已发布台账不可修改或删除，回退只能追加 `REVERSAL`，随后重建相关月度快照和报表投影。禁止直接更新余额字段。

## 四、按启用功能准备的数据

| 功能 | 需要客户提供 | 当前状态 |
| --- | --- | --- |
| 得力 E+ 打卡 | AppKey/Secret、租户初始化状态、每家公司来源、员工与得力人员标识映射、脱敏打卡样本 | 客户端和同步事务已实现；正式人员绑定、初始化/每日调度管理和真实租户验收未闭环 |
| OA 单据 | 只读库地址和账号、六类单据真实表结构、审批/撤回状态、主从键、枚举、时区、水位及脱敏样本 | 只有只读连接骨架和组织成员工号查询；业务单据 SQL 与同步尚未实现 |
| 离线打卡 Excel | 稳定来源编号、模板字段、时区、重复键和发布责任人 | 前端有入口，正式后端缺上传、预检和发布接口，当前不可用 |
| 员工自助 | 每名员工的本地账号和本人范围 | 本人今日工作台有正式读取；记录、假期、反馈的生产网关尚未接通 |
| 报表导出 | 导出角色、用途管理、保存期限和传递规则 | 查询/受控导出边界已存在，但必须先有正式投影 |

## 五、报表和首页还需要哪些“结果数据”

原始打卡和 OA 单据只是证据，不是报表行。目标处理链如下：

```text
员工/任职 + 班次/日历/考勤组/规则
                    +
              得力打卡 + OA 单据
                    ↓
          人员匹配、标准化与隔离
                    ↓
         每日确定性计算与异常状态
                    ↓
          月度不可变正式投影发布
                    ↓
       首页工作台、九类报表和受控导出
```

当前已有受信任的进程内投影发布能力，但缺少全月日结果持久化读取、OA 正式适配、时间账户月快照和月结后自动发布编排。因此“已经有原始数据”不等于首页/报表已经能自动显示。正式上线前必须补齐自动链路，或建立经过审批、可重复、可审计的内部批处理；不得让浏览器提交计算事实或直接发布投影。

## 六、客户资料交付清单

建议客户按公司分别交付并签字：

- 公司及组织树最终版；
- 员工、当前任职、历史调岗及二次入职边界；
- 管理员、高管、部门负责人名单及数据范围；
- 地点、班次、休息/用餐、跨日班次和年度日历；
- 迟到、早退、缺卡、补签、加班、请假、出勤率制度；
- 期初年假/调休/认可加班余额和余额基准日；
- 得力租户、人员映射和脱敏打卡样本；
- OA 六类表单字段说明与批准、拒绝、撤回、修改、跨月样本；
- 报表公式、列顺序、汇总层级、导出和留存要求；
- 上线日、历史追溯起点、并行对账周期及验收负责人。

## 七、逐公司上线门禁

- 组织树无断层，工号唯一，每名在职员工恰有一个当前任职；
- 每名应考勤员工在每个核算日恰有一个有效考勤组；
- 组所引用的地点、班次、日历和规则均有效且属于同一公司；
- 管理员角色和数据范围经过正向、反向权限验证；
- 得力启用时，来源、员工绑定、目标期间、同步样本和隔离数量均已验收；
- OA 启用时，字段签字矩阵完成并做影子对账；
- 假期启用时，期初台账合计与客户原账一致；
- 每家公司/月份存在最新正式投影，工作台、九类报表和导出抽样一致；
- 任一阻断项不通过时，不以演示数据、手工改库或隐藏错误继续上线。
