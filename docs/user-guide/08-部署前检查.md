# 08 部署前检查

## 当前结论

本机前后端和现有 V30 数据库可以继续验收，但当前仓库还不能从空库完整部署到 V30。原因是：V12～V28 已从原始 Git 对象恢复并校验，权威 V29、V30 迁移源文件仍待恢复。

不要自行编写同名 V29、V30，也不要使用 Flyway `repair` 掩盖 checksum 不一致。恢复原文件并通过校验后，才能把当前版本作为新的干净环境部署基线。

截至 2026-08-05，本机正式公司显示 615 名可开通候选；候选数不是账号数，尚未执行批量创建。只有在二次确认弹窗提交“确认开通 N 人”后才会写入账号。

## 部署前门禁

按顺序完成以下检查：

1. 从可信历史来源恢复权威 V29、V30 迁移文件。
2. 对目标数据库执行 Flyway `validate`，确认 V1～V30 版本和 checksum 全部一致。
3. 如果升级的是现有 W3 验证数据库，确认数据库已执行到 V30 后，再运行 `deploy/mysql/usability-finalization-post-v30.sql`；该脚本依赖 W3 基线记录，干净数据库不得运行。
4. 现有 W3 数据库应验证正式公司启用、W3 英文验证公司停用且业务页面不可见；干净部署则应验证 W3 公司根本不存在。
5. 现有 W3 数据库中的 4 个旧合成管理员记录会保留用于审计，但账号必须为 `DISABLED`、主体必须为 `INACTIVE`，旧登录会话和未使用的密码重置凭据必须已撤销；不得继续使用验收账号。
6. 验证浏览器验收产生的合成员工和合成组织已经清理，正式员工及考勤组归属均为 615 条。
7. 验证角色列表中不存在“制造中心主管/主任”，并确认历史上没有待处理的该角色授权。
8. 验证全部 6 个角色的菜单及数据范围：系统管理员、HR 管理员、高管、部门负责人、员工本人和审计只读。
9. 可以验证员工批量开通账号的预检和确认人数；未获得正式批准时，不得在二次确认弹窗提交“确认开通 N 人”。
10. 核对默认地点、班次、工作日历、考勤组、人员归属和规则生效状态。
11. 按公司采用的官方日历复核当年法定节假日与调休，必要时发布修订，并用少量样例人员校验结果。
12. 通过健康检查、后端测试、前端类型检查、单元测试和构建门禁。

## 密钥和管理员账号

- 数据库密码、系统管理员初始密码和会话密钥只能通过部署环境注入，不写入源码、迁移、手册、日志或提交记录。
- 设置稳定的 `SHENZHOUHR_PROVISIONING_PEPPER`：32 个随机字节、无填充 base64url 后恰好 43 位；只保存在部署密钥管理器。设置 `SHENZHOUHR_PROVISIONING_KEY_ID` 并记录轮换批次，轮换后未完成的账号清单必须走管理员密码重置，不能覆盖现有凭据。
- `SHENZHOUHR_PROVISIONING_RECOVERY_WINDOW` 默认 `PT1H`，不得超过 24 小时。生产入口必须使用 TLS，代理和访问日志不得记录 `Provisioning-Recovery-Key`。
- 首次部署完成后立即关闭管理员引导开关。
- 使用独立管理员账号完成验收，不与真实员工账号混用。
- 初始密码验证成功后立即修改，并确认旧会话已经失效。

## 首批账号开通建议

1. 先选择 1～2 名非敏感验收人员完成预检和开通。
2. 核对登录名等于工号、角色为“员工本人”、范围为“本人”。
3. 保存浏览器自动下载的本次临时凭据 CSV，并分别安全交付临时密码；该文件未加密且不会自动失效，使用完毕后应人工安全删除。
4. 验证首次登录强制修改密码。
5. 小批量验证无误后，再按公司实际安排分批或全部开通。
6. 模拟一次可重试的网络异常，确认同一批次复用请求标识和恢复键，不会重复创建账号或轮换密码，并能通过“重新确认上次批次”取得同一份有效临时密码清单。

## 部署完成后的检查

- 页面只显示账号有权访问的正式公司；单公司自动选中。
- 组织树、员工数量和任职部门与批准数据一致。
- 账号、角色和考勤配置页面不再出现测试术语或不明英文数据。
- 所有批量操作均有明确结果，失败时有可理解的中文原因。
- 操作记录中可以追踪账号创建、角色调整、规则发布和密码重置，但不包含明文密码。

生产或测试环境的实际发布、切流和数据迁移必须另行取得授权；本机验收不会自动连接或写入这些环境。
