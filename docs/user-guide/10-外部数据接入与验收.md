# 10 外部数据接入与验收

## 总体原则

外部系统连接成功只证明网络和凭据可用，不证明业务数据已经能进入考勤计算。每个来源都必须经过：固定只读合同、人员唯一匹配、幂等同步、原始记录留存、异常隔离、业务抽样对账和正式计算验证。

生产凭据只保存在客户服务器的根权限环境文件或密钥管理器中，不写入 Git、迁移、截图、聊天和普通日志。没有完成本章验收前，保持对应开关为 `false`。

## 一、得力 E+ 打卡

### 当前已经实现

- 只允许得力官方 HTTPS 地址和 `CHECKIN/checkin_query` 能力；
- AppKey/Secret 从环境注入，不进入源码；
- 按官方游标和最大 500 条分页，不自行猜测游标；
- 整页原始事实、标准化结果、人员匹配、隔离结果和水位在同一事务提交；
- 对限流、服务端错误和传输失败做有界重试；
- 原始 `check_data` 不进入业务日志；
- 每个来源绑定明确公司，并受权威考勤配置和期间状态保护；
- 只有已确认且唯一的员工绑定才允许成为有效打卡。

### 当前还没有完成

- 没有正式的员工—得力人员绑定维护页面/API；
- 没有可运行的租户初始化确认和每日自动调度管理链；
- 新建来源不会自动补齐初始化/每日操作记录；
- 设备/地点绑定没有正式维护入口；
- 真实租户曾完成只读连通探测，但返回零记录，尚未证明租户已初始化、历史范围可取或人员可匹配；
- 得力同步成功后到“日计算—月度投影—首页/报表”的自动链仍未闭环。

因此，得力客户端不能简单理解为“填入 Key/Secret 就会显示”。在人员绑定和调度能力补齐前，即使 API 返回记录，也可能因为无法唯一匹配而进入隔离，或因为目标月份没有 `OPEN/REOPENED` 正式投影而被阻断。

### 客户需要提供

- 正式或专用联调租户；
- AppKey、AppSecret 及权限范围说明；
- 租户是否已经执行官方初始化操作的证明；
- 每家公司对应的来源实例和历史追溯起点；
- 得力人员标识与内部工号的完整映射；
- 包含正常、跨日、重复、迟到、缺卡、撤回/修正场景的脱敏样本；
- 允许的同步频率、并发和 API 限额；
- 得力故障时的补数与人工处置责任人。

### 启用前步骤

1. 先完成公司、员工、任职、地点、班次、日历、考勤组和规则；
2. 为目标月份建立明确的 `OPEN` 或 `REOPENED` 期间；
3. 补齐并发布员工绑定维护能力，导入映射后确认零重复、零多匹配；
4. 以管理员 API 为每家公司注册一个正式来源；
5. 在根权限环境文件中填写凭据，先在联调环境启用；
6. 运行一小段时间范围，核对请求页数、水位、原始数量、匹配数量和隔离数量；
7. 抽取至少正常、重复、跨日、无法匹配和期间关闭五类样本；
8. 补齐每日调度和失败告警后，才启用自动运行；
9. 对日结果、首页、九类报表和导出做端到端对账。

### 应用环境变量

```text
DELI_EPLUS_ENABLED=false
DELI_EPLUS_BASE_URL=https://v2-api.delicloud.com
DELI_EPLUS_APP_KEY=
DELI_EPLUS_APP_SECRET=
DELI_EPLUS_PAGE_SIZE=500
DELI_EPLUS_CONNECT_TIMEOUT=PT5S
DELI_EPLUS_REQUEST_TIMEOUT=PT15S
DELI_EPLUS_MAX_RESPONSE_BYTES=4194304
DELI_EPLUS_SOURCE_TIME_ZONE=Asia/Shanghai
DELI_EPLUS_CREDENTIAL_REFERENCE_NAME=DELI_EPLUS_APP_CREDENTIALS
```

先填写并验收，最后才把 `DELI_EPLUS_ENABLED` 改为 `true`。不要为了测试而降低 HTTPS 校验、扩大响应上限或把密钥输出到命令行历史。

## 二、OA 考勤单据

### 当前已经实现

- 独立、默认关闭的 OA MySQL 只读连接池；
- 连接层只读保护、较小连接池和查询超时；
- 使用参数 SQL 从 `org_member` 按人员 ID 查询内部工号；
- 六类目标业务：出差、请假、加班、外出、免打卡、补签；
- 静态表/字段白名单和标准化领域合同；
- OA 来源页面可以读取已经同步进本系统的标准单据。

### 当前还没有完成

生产代码没有六类 OA 业务单据的固定查询、增量水位和同步任务。现有静态目录明确不是客户实库合同；审批状态、撤回链、主从关联、业务枚举、时区和日期边界均未签字。开发/测试环境的合成适配器不能用于生产。

所以，只配置 `OA_MYSQL_JDBC_URL`、账号和密码不会让 OA 页面、首页或报表出现数据。页面展示的是本系统已经标准化并同步的单据，不会直接把客户 OA 任意表透传出来。

### 客户需要提供

- OA 数据库类型、版本、地址和网络白名单；
- 专用只读账号及精确 `SELECT` GRANT；
- 六类表单主表/明细表的正式 DDL 或 metadata；
- 稳定业务主键、主从外键、创建/修改水位；
- 最终批准、拒绝、撤回、作废和修改后的权威状态值；
- 请假类型、加班类型、补签类型等完整封闭枚举；
- `DATETIME` 权威时区，日期区间结束日是否包含；
- 人员选择字段与 `org_member` 的关系；
- 每类表单批准、拒绝、撤回、修改、跨月、跨任职、多人/空人员等脱敏样本；
- 客户 DBA、OA 负责人和 HR 的联合签字人。

### 联调步骤

1. DBA 创建只读账号，只授予批准表和列的 `SELECT`；
2. 验证写入、DDL、非批准表查询均被拒绝；
3. 导出 metadata，逐项完成 OA 映射签字矩阵；
4. 为每类表单实现独立固定 SQL，所有参数绑定，不允许动态表名/列名；
5. 明确审批、撤回、修改和跨月规则，未知状态只隔离、不猜测；
6. 先运行影子同步，对比 OA 原始数量、有效数量、撤回数量和人员匹配；
7. 使用负例验证零行、多行、跨公司、空工号和未知枚举不会进入有效事实；
8. 完成日计算和正式投影自动发布后，再允许 OA 影响首页和报表；
9. 保留映射版本、查询摘要、对账记录和签字证据。

### 应用环境变量

```text
OA_MYSQL_ENABLED=false
OA_MYSQL_JDBC_URL=
OA_MYSQL_USERNAME=
OA_MYSQL_PASSWORD=
OA_MYSQL_MAX_POOL_SIZE=2
OA_MYSQL_CONNECTION_TIMEOUT=PT5S
OA_MYSQL_QUERY_TIMEOUT=PT3S
```

只读 JDBC 标记是第二道保护，不能代替数据库本身的最小权限。OA MySQL 不应使用 root、应用写账号或 `%` 来源主机授权。

## 三、能否直接调用其他打卡 API

可以新增其他厂商适配器，但不能把任意 JSON 直接当作正式打卡。新来源至少要冻结：

- 官方地址、鉴权、超时、限流和重试合同；
- 来源记录唯一键、增量游标、修改/删除语义；
- 原始时间、时区、设备和人员字段；
- 内部员工唯一绑定规则；
- 原始事实不可变、标准化和隔离策略；
- 公司、期间和考勤配置保护；
- 幂等、整页事务、水位 CAS、日志脱敏和审计；
- 真实样本及端到端报表对账。

未满足这些要求时，可以做只读探测或影子同步，但不能进入正式计算。

## 四、离线文件作为临时替代的限制

当前“打卡文件导入”前端展示了上传、预检和发布流程，但正式后端只有模板及任务/错误查询，没有上传、预检和发布写接口。现阶段不能把它作为得力或 OA 的上线替代方案，也不能由 DBA 直接把 Excel 内容插入打卡表。

若客户需要离线兜底，应先补齐：病毒/大小/类型校验、模板版本、预检、重复键、人员和时区匹配、差异确认、幂等发布、批次回退、审计和权限测试。

## 五、生产验收证据

每个来源至少留存以下不含敏感明文的证据：

- 环境和版本标识；
- 配置开关、凭据引用名及权限证明，不记录密钥；
- 请求时间范围、页数、源记录数、去重数、匹配数、隔离数；
- 水位前后值和重复运行的幂等结果；
- 失败重试、永久失败和恢复演练；
- 人员/公司/期间越权负例；
- 日结果与客户原系统的抽样对账；
- 首页、九类报表和导出的同版本一致性；
- 客户 HR、IT/DBA 和实施方签字。
