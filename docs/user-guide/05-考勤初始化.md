# 05 考勤设置详解与初始化

## 先看懂整套关系

考勤设置不是 6 套互不相关的功能。它们共同回答 6 个问题：

| 功能 | 回答的问题 | 通常由谁维护 | 常见调整频率 |
| --- | --- | --- | --- |
| 公司 | 这是谁的数据？ | 系统管理员 | 很少 |
| 地点 | 员工在哪里、按哪个时区考勤？ | HR 管理员 | 很少 |
| 班次 | 一天几点上班、休息和下班？ | HR/考勤管理员 | 班制变化时 |
| 工作日历（考勤日历） | 哪一天上班、放假或调休？ | HR/考勤管理员 | 每年至少一次 |
| 考勤组 | 哪些员工使用哪套地点、班次和日历？ | HR/考勤管理员 | 入职或班制变化时 |
| 考勤规则 | 迟到、早退、缺卡、加班等如何判断？ | HR/考勤负责人 | 制度变化时 |

它们的组合关系是：

```text
集团共享地点目录：在哪里、什么时区（只维护一份）
└─ 公司可用关系：哪些公司可以选择该地点

公司
├─ 班次：一天的时间安排
├─ 工作日历：一年中每天的性质
├─ 考勤规则：如何计算和判定
└─ 考勤组
   ├─ 选择 1 个地点
   ├─ 选择 1 套默认班次
   ├─ 选择 1 份工作日历
   └─ 分配需要采用这套安排的员工
```

系统计算某名员工某天的考勤时，会先找到该员工当天有效的考勤组，再取得地点、班次、日历和规则，最后结合打卡及 OA 请假、加班等数据生成结果。

## 规则中心是什么

“规则设置”是考勤配置的入口页，不是另一套独立规则。日常可以按：考勤组页面中的考勤地点 → 班次 → 工作日历 → 考勤组 → 考勤规则的顺序完成。当前没有单独的“地点”菜单，地点维护位于“考勤组”页面的“考勤地点”区域。

大多数公司完成这 5 步就可以开始核对考勤。页面底部的“高级功能”只用于复杂策略的模板、版本、生效范围和发布管理，一般 HR 不需要每天进入。

## 1. 地点：在哪里考勤

地点用于确定物理工作地点和时区。它不负责设置上下班时间，也不等于部门。地点主数据由集团统一维护，不因公司不同而复制；公司只记录“可以使用哪些共享地点”。

当前版本的地点主要承担共享物理地点标识、名称、时区及公司可用关系校验，不包含 GPS 围栏、Wi-Fi 范围或考勤机网络地址。

本期地点目录已按确认范围锁定为 7 个，页面不提供“新建地点”。如将来真的新增厂区或海外办公点，应先由系统管理员审批并升级共享目录功能，不能在单一公司下直接复制一条同名地点。下列情况可作为届时的审批依据：

- 集团新增了实际厂区或办公区；
- 不同地点使用不同时区；
- 后续需要按地点隔离考勤来源或规则。

不需要新增地点的情况：

- 只是部门不同，但在同一厂区、同一时区上班；
- 只是白班、夜班不同，这应通过班次和考勤组处理；
- 只是某一天临时调班，这应通过日历或后续生效版本处理。

地点编码是稳定标识，例如 `SHANGHAI`、`YANGZHOU`，日常可以修订业务人员看得懂的中文名称。当前人员都在中国，系统起步值为“中国标准时间（上海）”，时区下拉框继续保留：尚未投入考勤使用的地点可以选择其他时区；已经被班次、日历或考勤组引用的地点，为保护历史结果不能直接改时区，需要由系统管理员评估受控迁移。

地点名称和时区只修订一次，所有已关联公司看到的是同一份主数据。为了避免单公司操作影响其他公司，修改共享地点主数据需要覆盖其全部关联公司的系统级管理权限；普通公司管理员只在本公司考勤配置中选择共享地点，不能静默修改其他公司的地点名称或时区。

## 2. 班次：一天几点上班

班次描述一天内的时间段，例如：

- 工作：08:30～12:00；
- 休息：12:00～13:00；
- 工作：13:00～17:30；
- 夏令安排：13:00～18:00；
- 夜班：当天 20:00 至次日 08:00。

“班次模板”是稳定名称，“班次版本”是某个日期起生效的具体时间。冬令、夏令或制度调整时，应追加后续生效版本，不要覆盖已经用于历史计算的版本。

发布前重点核对：

- 至少有一个工作时段；
- 时间段不重叠、不倒置；
- 休息和用餐时间符合制度；
- 跨日班次的结束日偏移正确；
- 生效日与上一版本衔接，没有空档或错误重叠。

## 3. 工作日历：哪一天上班

工作日历也可以理解为“考勤日历”。它给全年每个日期标注性质：

- 工作日；
- 周末；
- 法定节假日；
- 调休工作日。

工作日历不负责保存员工名单。它通常以公司、地点和年度为单位维护。特殊日期确实需要采用不同班次时，可以设置临时班次覆盖；普通日期留空，沿用考勤组的默认班次即可。

每年应根据公司正式采用的节假日通知逐日复核。默认日历只是起步数据，不能替代公司最终发布的日历。

## 4. 考勤组：把配置真正分给员工

考勤组是整套配置的“装配点”。一个考勤组会固定关联：所属公司、地点、默认班次、工作日历和生效日期，然后再把员工分配进来。

最常见的划分方式：

- 同公司、同地点、同班次、同日历：一个考勤组即可；
- 同一地点有白班和夜班：建立两个班次、两个考勤组；
- 两个地点假期安排不同：分别建立地点、日历和考勤组；
- 管理人员和一线员工采用不同规则：分别建立考勤组并绑定相应规则。

每名应考勤员工在同一日期只能有一个有效考勤组。调部门不一定要换考勤组；只有地点、班次、日历或规则实际发生变化时才需要调整。

调整时填写新的生效日。系统保留旧归属用于历史核算，不应删除或覆盖已经生效的记录。

## 5. 考勤规则：结果怎么算

当前页面和运行时已正式接入 3 类可维护规则：

| 规则 | 用途 | 当前起步值需要关注什么 |
| --- | --- | --- |
| 用餐扣除 | 晚餐、周末及节假日用餐时间如何扣除 | 含冬夏令及周末/节假日参数，必须复核 |
| 迟到宽限 | 上班时间后多少分钟开始计迟到 | 起步宽限 15 分钟，需确认公司制度 |
| 每月迟到豁免 | 每月允许几次指定范围内的迟到 | 起步值每月 1 次、15 分钟内，需确认 |

每家公司都有这 3 类已发布版本，默认考勤组和江苏神州 3 个特殊组也分别建立了显式绑定。修改后必须完成校验、影响预览和发布；只保存草稿不会用于正式解析。

数据库还保留了早退、缺卡与补签、打卡归属与配对、加班认定、出勤率 5 类起步记录，供后续功能接入时迁移使用。但当前版本没有把这 5 类开放到考勤规则页面，也不能把它们描述为已经进入正式配置解析或计算。正式启用前需要补齐业务口径、页面、接口、解析和测试；不要仅修改数据库参数后用于核算。

## 6. 高级功能：什么时候才用

高级功能用于维护通用的“高级规则模板”，主要能力包括：

- 定义复杂规则的可配置字段；
- 创建草稿和后续版本；
- 指定公司、地点、考勤组或策略组等生效范围；
- 设置生效与失效日期；
- 做参数校验、冲突检测和样例试算；
- 发布、停用、恢复并保留完整变更记录。

以下情况才建议进入高级功能：

- 常规考勤规则页面无法表达公司的特殊制度；
- 同一规则需要按多个范围和优先级覆盖；
- 需要严格的草稿、复核、发布流程；
- 需要查看或审计历史规则版本。

普通的上下班时间、节假日、人员分组和上述 3 类已接入规则，应优先在日常考勤设置中完成。高级模板不是另外 5 类考勤规则的替代入口。看不懂高级模板时不要尝试删除或随意发布；先确认业务规则，再由有规则管理权限的人员处理。

## 以后如何修改预置值

调整班次、日历、考勤组、人员和规则前，先在页面顶部选择正确公司。多公司账号必须明确选择公司；只有一家授权公司时系统才会自动选中。地点主数据是集团共享项，不应随公司切换出现多份同名记录。

### 修改地点名称或时区

1. 进入“规则设置 → 考勤组”，在“共享考勤地点”区域找到目标地点并打开修订；
2. 确认该地点关联的公司范围，填写新的名称、时区、生效日和变更原因；
3. 保存后检查“修订历史”和当前生效状态；
4. 保存后核对所有关联公司看到的名称和时区一致；如果某个考勤组要改用其他地点，再给该公司的考勤组创建后继修订。

地点编码是稳定标识，已经建立后不能通过修订改成另一个编码。地点名称通过后继修订修改，旧日期仍保留旧修订用于追溯。时区变化会影响全部关联公司：未被班次、日历或考勤组引用的地点可以保存新的时区；已有任何考勤配置或历史引用时，系统会拒绝直接修改并提示联系系统管理员评估受控迁移，不能只改页面显示。当前页面保留中国标准时间和新加坡时间两个选项。

### 修改上下班时间

1. 进入“考勤设置 → 班次”，打开要调整的班次模板；
2. 新建一个后续班次版本，填写生效日和工作、休息时段；
3. 校验时间段没有重叠、倒置或错误跨日；
4. 发布新版本，并检查发布边界前后各能解析出一个有效版本；
5. 用一名受影响员工和一个生效日后的日期做样例核对。

已经发布的班次版本不可原地修改。调整大连、成都或扬州时间时，都按上述方式新增版本；上海考勤组当前只是独立复制了扬州 2026 时间，不会自动跟随扬州后续版本。需要同步或改成独立上海时间时，应单独创建上海班次版本并修改上海考勤组。

### 修改节假日或调休

1. 进入“考勤设置 → 工作日历”；
2. 为目标年度创建草稿版本；
3. 逐日设置工作日、周末、法定节假日和调休工作日；
4. 确认有效期间内每一天都已配置；
5. 校验并发布，再检查引用该日历的考勤组。

已经发布的日历也不原地覆盖。2027 年开始前，应提前建立 2027 日历和对应生效版本。

### 修改人员使用的地点或班次

1. 先确认目标地点、班次和日历已经存在且已发布；
2. 进入“考勤设置 → 考勤组”，创建或编辑目标考勤组的后继修订；
3. 选择地点、默认班次、工作日历和生效日；
4. 在“分配人员”中把员工从指定日期起调整到目标组；
5. 检查该员工在任一业务日都只有一个有效考勤组。

部门变化不会自动改变考勤时间。员工只有在实际地点、班次、日历或规则发生变化时才需要调整考勤组。

### 修改迟到、缺卡、加班等规则

1. 进入“规则设置 → 考勤规则”，选择公司和已接入的 3 类规则之一；
2. 创建草稿或后续版本，填写参数、生效日期和原因；
3. 先校验，再查看冲突和影响预览；
4. 发布后，将需要采用它的考勤组绑定到这个已发布版本；
5. 出现问题时使用停用、恢复或回滚流程，不要覆盖原版本。

当前页面只支持用餐扣除、迟到宽限和每月迟到豁免。其他 5 类仍需后续产品版本接入，不要按照本节直接修改。修改前先看影响人员和月份；已经月结的期间如需重算，由系统管理员按受控流程处理，不能仅靠改配置自动改写历史结果。

### 修改完成后必须检查

- 当前公司、版本号、生效日和变更原因正确；
- 受影响人员数量符合预期；
- 生效日前仍使用旧版本，生效日起使用新版本；
- 不存在同一天多个考勤组、无班次或无日历的空档；
- 操作记录中能看到创建、校验、发布、停用或恢复记录。

这些配置用于保证系统部署后有可检查的完整链路，不代表 4 家公司的制度永远完全相同。正式计算前，HR 仍要逐家公司复核节假日、迟到宽限、用餐扣除、加班、请假和出勤率口径。

## 第一次检查的推荐顺序

先检查一次共享地点目录，再对每家公司分别执行其余配置检查：

1. 核对全集团地点总数为 7，名称为扬州、成都、大连、上海、合肥、武汉、深圳；
2. 在公司下拉框中选择目标公司，确认它可以从这 7 个共享地点中选择且默认组使用扬州；
3. 核对默认冬夏令班次，以及大连、成都、上海特殊组；
4. 核对 2026 工作日历的节假日和调休；
5. 打开默认考勤组，核对地点、班次、日历和员工人数；
6. 核对 3 类已接入规则及考勤组绑定，并确认另 5 类尚未启用；
7. 选择少量非敏感样例员工，测试普通工作日、周末、节假日、迟到、缺卡和用餐扣除；
8. 确认切换公司后不会看到上一家公司的员工和配置。

## 一个简单例子

假设江苏神州的员工张三在江苏厂区执行白班：

1. 张三当前属于“江苏神州默认考勤组”；
2. 该组选择默认地点“扬州”；
3. 该组使用“标准冬夏令班次”；
4. 2026-08-10 在工作日历中是工作日；
5. 系统按当天有效班次取得应上班时间；
6. 再按迟到、缺卡、用餐和加班规则处理打卡及 OA 数据；
7. 最终结果进入工作台和报表。

如果张三改成夜班，只需从指定日期起调整到夜班考勤组，不需要修改他的公司或部门。

## 初始化完成检查

- 公司下拉框可以在 4 家授权公司之间切换；
- 四家公司的组织、员工和考勤配置互不串用；
- 全集团只有扬州、成都、大连、上海、合肥、武汉、深圳 7 个共享地点；4 家公司各有 7 条可用关系，但没有复制地点主数据；
- 每名应考勤员工都有且只有一个当前有效考勤组；

- 规则和配置的生效日期连续且合理；
- 样例计算结果与公司制度一致；
- 变更记录中可以追踪配置、校验和发布操作。
