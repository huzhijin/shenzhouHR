## Context

当前报表 GET 链只读取 `PUBLISHED` 月度投影，完整计算器则位于发布编排器内部。得力和 OA 已通过只读适配器进入本地不可变证据表，班次、考勤组、日历、人员任职和组织版本也已有批量读取 Mapper。参见 [proposal.md](proposal.md) 与实时查询规格。

直接在每次报表请求中访问外部得力/OA 网络既慢又无法形成一致快照，因此“实时”定义为：以两个来源最新成功提交的本地水位为截止点，请求时计算；不是等待人工发布，也不是每次请求远程拉取。

## Goals / Non-Goals

**Goals:**

- 保持现有报表 GET 和前端主要合同，移除 `PUBLISHED` 投影前置条件。
- 一次批量装载得力/OA/班次/考勤组/组织人员输入，复用确定性日计算和报表组装。
- 在进入公司月计算前确认目标公司授权；每次响应重新解析当前人员/组织范围，并在任何报表聚合前过滤不可变计算事实。
- 用得力/OA 已提交水位和完整计算输出的确定性摘要生成快照令牌，并用短时有界缓存满足极速重复查询。
- 来源缺失、歧义或未支持单据继续失败关闭。

**Non-Goals:**

- 不在报表请求线程内调用得力或 OA 外部接口。
- 不删除现有投影表、发布记录和审计代码；它们暂时作为兼容能力保留，但不参与默认读取。
- 不用 SQL 或旧投影字段猜测新业务事实。
- 不放松现有公司、组织、本人数据范围，也不允许系统管理员隐式跨公司读取。

## Decisions

### Decision 1: Reuse the side-effect-free batch calculation core

现有完整计算编排器的 `assemble` 本身只批量读取并返回内存中的日事实、OA 报表事实、账户事实、来源版本及确定性计算摘要，不执行投影写入。将其合同明确为无副作用的公司月计算核心；实时查询服务直接消费结果，兼容发布服务如继续使用，则在同一结果之后另行持久化。

选择该方案而不是再提取一层同义服务或在 GET 内调用发布接口，是为了保持实现简单，同时避免数据库写入、状态机和审计副作用。选择复用现有计算器而不是另写一套 SQL 统计，是为了避免实时与发布口径分叉。

### Decision 2: Resolve authorization before loading calculation inputs

查询服务先校验 `ATTENDANCE_REPORT:READ`，再在数据库中解析当前主体对目标公司的有效 scope 与授权员工 ID。目标公司完全不在授权范围时，不启动计算且不泄露数据是否存在。

为了让多个组织范围共享一次极速公司月计算，短时缓存可持有该公司的不可变计算事实，但绝不缓存权限结果。每个请求都重新解析当前 scope，在传给报表计算器和任何聚合之前按授权员工、授权组织以及客户端筛选取交集。公司级聚合只有 COMPANY scope 可见；组织和 SELF 无法从不可见员工的汇总值推断信息。

### Decision 3: Snapshot token replaces projection dependency

当前实现汇总得力/OA committed watermark，并对本次完整计算输出（包括人员/组织展示身份、日事实、OA 报表事实和账户事实）做确定性摘要，规范化后计算 SHA-256 作为 `snapshotToken`。现有响应中的 `projectionVersion` 暂时承载该 token，以保持客户端兼容；新文档将字段解释为查询快照版本。

这保证计算输出变化时 token 同步变化，但当前尚未实现覆盖全部人员和配置表版本的独立轻量查询，不能把 token 描述为完整配置版本目录。分页和下钻可携带同一 token；若 token 已变化且缓存中没有旧结果，返回可重试的 `ATTENDANCE_REPORT_SNAPSHOT_CHANGED`，不混合两个快照。导出尚未接入该 token，因此默认报表界面不提供生产导出。

### Decision 4: Bounded snapshot-aware cache

使用进程内有界缓存，key 包含 company、period 和 30 秒计算截止桶；值为未授权展示的公司月不可变计算事实。权限不缓存，每次命中后仍重新解析并过滤。活动桶最多使新提交的本地证据延迟 30 秒可见；首屏 token 对应的旧结果最多保留 5 分钟供分页一致性使用，同时限制最大 company-month 条目数，并记录 hit/miss/eviction/计算时延指标。

缓存 key 不直接包含来源水位或全部配置版本；新提交的得力/OA 证据以及配置变化最迟在进入下一个 30 秒桶后重新计算并反映到新 token。多实例可各自计算，结果由来源水位和确定性完整输出摘要约束；本轮不引入 Redis 等新外部依赖。

### Decision 5: Keep source synchronization explicit and read-only

OA 连接保持 SELECT-only。得力/OA 同步将成功页原子提交到本地证据表并推进各自来源水位；报表仅读取已提交到本地的证据，不在报表请求线程直连外部系统。部署后可执行来源同步，存在已提交水位后即可查询报表，不增加报表发布或审批步骤。

同步成功不等于计算可用：无法解析的销假、未知假别、身份歧义、班次或策略歧义都作为安全错误返回，不静默过滤。当前没有签署的数据年龄阈值，因此只暴露实际来源截止时间，不基于任意年龄把已提交水位判为 stale；年龄型 freshness contract 及其错误码仍待实现。

### Decision 6: Preserve API shape and remove publication from the UI path

`GET /api/v1/attendance-reports`、公司选项和报表页面改用实时服务。前端不显示“请先发布”的操作要求，而显示“数据截止时间/刷新”。旧 publication API 可以暂时保留给兼容调用，但不得成为读取前置条件，也不在默认界面暴露。生产导出和仪表盘尚未切换到同一实时快照，因此不作为本次已完成的默认报表能力。

## Risks / Trade-offs

- [冷查询对大公司计算量高] → 先按授权范围批量装载、禁止 N+1、缓存 company-month 事实并建立 5,000 员工性能门禁。
- [短缓存与“当前”含义产生误解] → 响应显示 Deli/OA 水位和 `dataAsOf`，并明确活动桶最多带来 30 秒可见性延迟。
- [多实例重复计算] → 接受短时 CPU 重复以避免引入新基础设施，结果由同一 token 和确定性摘要验证。
- [必需来源尚无已提交水位导致报表不可用] → 显示来源状态和安全错误，不以零考勤降级；已有旧水位时显示真实截止时间，不在没有签署阈值时擅自判定年龄陈旧。
- [既有导出/仪表盘依赖投影] → 首批先切换核心报表 GET，再复用同一实时快照服务切换导出和仪表盘；未切换消费者不得误标完成。

## Migration Plan

1. 提取并验证无数据库写入的批量计算服务，保留原发布路径回归。
2. 实现授权范围解析、基于来源水位与完整计算输出摘要的 token 和有界缓存；完整配置版本查询作为后续增强。
3. 将核心报表 GET/公司选项切到实时服务，前端显示来源截止时间并移除发布前置提示。
4. 后续将导出和仪表盘切到同一 token；在此之前保持生产导出隐藏，不把仪表盘称为实时报表消费者。
5. 待客户环境可用时，对单一公司/月执行得力+OA同步、冷/热性能和人工样本对账；该步骤尚未完成。
6. 部署时保留原表和代码以便制品回退；回退旧制品后恢复旧投影读取，不删除新同步证据。
