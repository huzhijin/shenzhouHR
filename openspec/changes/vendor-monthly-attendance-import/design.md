## Context

现有打卡导入（`punchimport`）只解析官方六工作表模板，一行一次打卡，结果列直接拒绝。客户交付的历史数据是两种厂商月报：

- `月度汇总表_YYYYMMDD_YYYYMMDD.xlsx`：姓名/工号/部门 + 汇总列 + `周三\n26-07-01` 日列；每人两行（进/出）；格子为 `HH:MM` 或 `-`。
- 得力 `考勤月报-…xlsx`：帐号/工号/姓名 + `01/三` 日列；签到/签退成对；格子为 `HH:MM`、`HH:MM 迟到|早退` 或 `漏刷`。

7 月曾用一次性 SQL 从这两份表抽出约 2.5 万个时间点写入证据链，并修过组织生效日前缀。产品页面仍不能吃这两种表。得力 API 按 `next_id` 增量，拉不到 1–7 月。OA 1–7 月单据已在库。人员主数据多半从 2026-08-04 起算，实时报表选 1–7 月会因身份 `validOn` 失败而跳过。

报表中心已经按筛选月份做 LIVE 计算，不读不写 `attendance_report_projection`。导入后不需要再发布月报。

## Goals / Non-Goals

**Goals:**

- 在现有导入批次状态机上识别并拆两种月报，按工号匹配后发布打卡事实。
- 凡已存在的打卡一律精确去重（不限月份、不限来源）；同月两份文件是并集。
- 预检留批次；有问题必须确认后才发布有效行。
- 一次性把当前员工/任职/部门/考勤组生效日拉到 `2026-01-01`，只改当前敞口版本。
- 报表继续按筛选日期实时算（打卡 ∪ 已有 OA）。

**Non-Goals:**

- 不还原 1–7 月部门调岗、历史组织树。
- 不从月报导入迟到/早退/旷工/请假汇总，不把厂商结论当本系统结果。
- 不发布月报投影，不自动跑整月重算/关账。
- 不改官方六工作表模板合同，不改得出勤公式，不改得力/OA 同步。
- 不给无工号人员做姓名猜测。
- 不把身份前移塞进每月 Excel 发布事务。

## Decisions

### 1. 适配器接在解析层，不另开导入产品

在 `PoiPunchWorkbookGateway.parse` 先做安全信封/ZIP/公式检查，再按表头分类：官方模板、月度汇总表、得力月报。后两种拆成与官方模板相同的 `employeeNumber / punchTime / direction` 行，再进入现有 precheck / fingerprint / publish。

备选：线下转成官方模板再上传。否决：操作员每月要手工拆 1 万+ 格，且无法在产品里留同源批次。

### 2. 拆格口径固定

- 日期来自日列表头（`26-07-01` 或 `01/三` + 文件/标题年月）。
- 方向：汇总表按人块第一行 IN、第二行 OUT；得力表按「签到/签退」。
- 时间：正则取出 `H:MM`/`HH:MM`，秒补 `:00`，时区沿用公司业务时区。
- 丢弃：空、`-`、`漏刷`、纯状态字、汇总列。
- `08:30 迟到` → `08:30`，结论字丢掉。
- 拆后行数计入 50,000 上限。按月分批，1–7 月禁止打成一个文件。

### 3. 只按所选公司内工号匹配

上传仍选一个公司。工号在该公司内唯一且任职覆盖打卡时刻才匹配。帐号、姓名、部门只比对。无工号或公司内不唯一 → 阻断行，确认后跳过。7 月旧例外名单删除，已纠正的工号按新主数据匹配。

### 4. 有问题走现有部分发布，而不是静默跳过

默认向操作员展示预检清单并弹出确认。确认调用已有 `VALID_ROWS_ONLY`。取消则批次留着、不写事实。严格整批发布仍保留给无阻断的月份。

### 5. 已有数据一律去重

去重键：所选公司内匹配到的员工 + 规范化打卡时刻（日期 + `HH:MM:00` + 业务时区）+ 方向。来源不参与是否重复的判断。库里已有有效事件（得力、官方模板、月报、SQL 回填、同月另一文件）则记精确重复，不新增有效事件；没有则新建。两边原始事实可以都留。预检要把「新增 / 重复」条数亮给操作员。这是默认规则，不是 7 月特例。

### 6. 发布打卡 ≠ 发布报表

批次发布只写 raw / effective punch。不调用报表投影发布，不创建公司月重算作业。操作员到报表中心选月份即 LIVE 查询。现有窄范围 recalculation intent 若仍由证据链写入，不得被编排成自动出正式月报。

### 7. 身份一刀切是独立、有条件的 UPDATE

先只读诊断，再把每个对象**最早一条版本**的 `effective_from` 前移到 `2026-01-01`（7 月已补过前缀的人只动最早那段，不把多条历史叠到同一天）。范围：

- `employee_version`
- `employment_assignment`
- `organization_version`（当前部门，含为了 `validOn` 必须覆盖的上级版本）
- `attendance_group_assignment`
- 若考勤组修订/日历/政策也从 8 月才生效，同一规则前移当前敞口修订，否则 1 月 LIVE 计算会因缺班次整月失败

禁止把同一对象的多条版本都改成 1 月 1 日。历史调岗不补。与导入分两步执行：先切身份，再用 1 月两份表验收。

备选：为每人新增一条 1–8 月历史版本。否决：客户明确不还原调岗，多一条版本增加重叠风险。

## Risks / Trade-offs

- [1–7 月报表部门都是当前部门] → 已接受；在操作说明里写明。
- [只改人、不改考勤组/日历，1 月整月算挂] → 诊断必须覆盖考勤组修订、日历、政策；缺一则停。
- [多版本被一并改到 1 月 1 日 → 身份歧义，整月失败] → 只改当前敞口一条，重叠硬停。
- [无工号约 17 人进不了] → 确认后留在问题清单，不猜。
- [公司内仍有重复工号] → 预检阻断，等人改主数据后再导，不静默跳过。
- [任意已有打卡再导] → 精确重复，0 条新有效事件，批次可查；只有文件里多出来的时间才新建。
- [厂商以后改表头] → 分类失败即拒绝，不模糊解析。
- [拆格后接近行上限] → 按月、按文件；单月两份约 2 万行，可接受。

## Migration Plan

1. 备份生产库。
2. 跑身份诊断；对可前移对象执行一刀切；幂等重跑应 already-applied。
3. 部署月报适配器（后端解析 + 前端确认文案）。官方模板路径回归。
4. 用 2026-01 两份样例上传 → 预检 → 确认 → 发布打卡。报表选 2026-01 能看到人、打卡和 OA。
5. 再按月导 2–7 月。任一月与库中已有时间重叠的部分只去重，只补缺口。
6. 回滚：适配器可通过来源类型关闭或回退发布包；身份前移用审计里的旧 `effective_from` 回写当前版本（仅当该版本仍是当前敞口且未被后来编辑）。

## Open Questions

- 若诊断发现个别考勤组/日历无法安全前移，是整批停还是列出后继续可前移对象？默认整批停，避免 1 月部分人有班次、部分人把整月算挂。
- 上传页是否一次选两个文件，还是沿用现有「一次一个文件、同月连传两次」？默认沿用现有一次一个文件，降低批次模型改动。
