## Why

客户手里的历史考勤只有两种厂商月报 Excel（`月度汇总表`、得力`考勤月报`），得力 API 拉不到 2026 年 1–7 月打卡。现有导入只吃官方一行一打卡模板，这两种表过不了门；人员/部门/考勤组又多半从 8 月导入日起算，选 1–7 月实时查询时人会消失。现在就要按月把历史打卡补进证据链，让报表按筛选月份现查现算。

## What Changes

- 现有「外部考勤电子表格导入」增加两种厂商月报识别与拆格：只抽取 `HH:MM` 打卡时间，忽略颜色、漏刷、`-`、迟到/早退文字和汇总结果列。
- 同一自然月可连续上传两份互补月报，按工号匹配后做并集。
- 凡是库里已经存在的打卡（得力同步、以往 Excel、一次性 SQL、同月另一份月报、本文件重导）一律走精确去重：同一员工 + 同一时刻 + 同一方向只保留一条有效事件，新来源可留原始行，不插第二条有效事件。新时间照常入库。
- 预检必须留下批次记录。对不上的工号、无工号行、已存在重复打卡等弹出确认；确认后只发布有效新行，重复与问题行留在该批次。
- 导入只发布打卡事实，不发布月报投影，不自动触发整月重算。报表中心按筛选日期实时查询（打卡 ∪ 已有 OA 1–7 月单据）。
- 一次性把当前敞口的员工版本、任职、部门版本、考勤组分配生效日前移到 `2026-01-01`。不还原历史调岗；每个对象只改当前那一条，禁止把多条版本都改成同一天。
- 不再保留 7 月冲突工号例外名单（主数据工号已纠正）。
- 官方六工作表模板导入路径保持不变。

## Capabilities

### New Capabilities

- `identity-effective-from-cutover`: 一次性、可审计地把当前员工/任职/部门/考勤组生效日拉到 `2026-01-01`，使 1–7 月实时计算能解析到唯一身份。

### Modified Capabilities

- `attendance-punch-imports`: 在现有批次/预检/部分发布/追溯之上，接受两种厂商月报为打卡时间容器；工号匹配；有问题须确认后才发布有效行；发布后不接月报投影或自动重算。

## Impact

- 后端：`punchimport` 解析增加月报适配器；拆出的行仍进入现有 raw → match → effective 证据链。身份前移是一次性主数据修复，与每月导入分开执行。
- 前端：`/sources/attendance-excel` 支持厂商月报上传、预检问题确认、批次留痕。报表中心筛选月份的 LIVE 查询不改合同。
- 数据：1–7 月按月分批，单月拆格后低于 50,000 行上限。无工号行确认后仍不入库。
- 不改得力增量同步、不改 OA 同步、不改官方模板字段合同、不改出勤公式。
